Scope: PR #6 (`feat/fa4-launch-config`). Nothing here is deployed to production. Facts only; anything external is marked **EXTERNAL**.

## 1. Delivery semantics (D-156, Option 2)

| State | What exists | Editable | Regenerable |
|---|---|---|---|
| In progress / **YEV preview** | Nothing stored in `fa4_result`. `POST /session/result` computes the YEV from the current answers and returns `preview: true` + `previewToken`. Event `yev_previewed`. | yes («Corregir algo») | yes |
| **DELIVERED** | One sealed `fa4_result` row (A+ envelope). Project `status = DELIVERED`. Event `yev_delivered` (once). | **no** (API 409 `ALREADY_DELIVERED`; DB trigger BV604 on `fa4_project.answers`) | **no** |

Delivery happens only through two explicit actions, both idempotent and concurrency-safe (partial unique index `fa4_result_one_sealed_per_project`):

1. `POST /session/result/email` — asking for the result by email *is* the delivery; the email is queued for **that** sealed `result_id`.
2. `POST /session/continue` — «Comienza tu expansión» / «Start your expansion», after an explicit confirmation step in the UI. Delivers (if not yet delivered), then records the continuation on `project_id + result_id`. No payment/checkout.

`previewToken` = sha256 of the canonical source snapshot + `catalog_version` + `RULES_VERSION`. A delivery that presents a token refuses to seal anything the client has not seen (`409 STALE_PREVIEW`). No Result B, no timers, no auto-delivery.

Database safety net (migration 0023, deferred constraint triggers; proven under real commits in `fa4-v1-delivery.int.test.ts`):
BV604 closed answers after delivery · BV605 `DELIVERED ⇔ sealed result` · BV606 a continuation can only point at a sealed result of the same project.

## 2. Commercial traction (D-153)

Old semantics (stored value `via_third`): "operates/sells in the destination through a third party". Real downstream use: **no rule, YEV text, Precision mapping or demand signal reads it** (it only drives the presence follow-up question and is echoed in the source snapshot).
New: `ExistingInDest = 'nothing' | 'commercial_traction' | 'via_third' | 'own'` — `commercial_traction` = existing customer, pending order, advanced prospect or commercial conversation in that country, **without** own presence and **without** a third party operating it. Per component × destination, never a generic yes. Optional free note (`existingNote`).
- `via_third` is **kept as a legacy value** (historical answers stay valid and replayable); the UI shows it as «commercial traction» without rewriting stored data. New sessions never write it.
- Rules / YEV / Precision: no rule change; the value is carried as a declared fact in `SourceSnapshotV1` and the Precision context. `RULES_VERSION` bumped (`fa4-rules/2026-10-14.1`) and pinned by `rules-golden.test.ts`.
- Migration: none needed for data (enum widening only; JSON answers).

## 3. A+ envelope (D-157) — `fa4_result` (sealed row)

`catalog_version` · `rules_version` · `source_schema_version` + `source_snapshot` (client-safe business facts; **no** email, legal, marketing, contact PII) · `resolution_schema_version` + `resolution_snapshot` (sanitized stable projection; **no** traces, provider names, sourcing fields) · `model` (historical YEV, kept for display only; never read by Precision). Immutable for the application (no UPDATE/DELETE grant) and for SQL (BV601 append-only triggers). Sealed-envelope CHECK: a non-legacy row must carry the entire envelope.

## 4. `Fa4PrecisionContextV1` (D-158)

`getFa4PrecisionContext(db, project_id, result_id)` (`backend/src/fa4/precision.ts`) → pure mapper `mapSealedResultToPrecisionContext` (`shared/fa-public-engine/src/precision/context.ts`). Reads **only** the sealed row. Does not read mutable Answers, does not re-run rules, does not read the current catalog, does not parse the YEV `model`, no AI. Output: `versions`, `declared` (provenance `DECLARED_BY_USER`), `derived` (provenance `DERIVED_FROM_FA`), structured `openStates`. Not eligible (NOT_FOUND): previews, legacy rows, other projects' results. Anonymized results → `NOT_RECOVERABLE`.
Field coverage matrix (INCLUDED / EXCLUDED / RESTRICTED / NOT_APPLICABLE per answer path): `docs/fa4/FIELD_COVERAGE_MATRIX.md` (generated by `npm run fa4:coverage-doc`; a unit test fails on drift).
**Legacy contracts** (`fa-core` Precision handoff, `getFirstAssessmentPrecisionContext`, Snapshot v1): untouched, **LEGACY**, not consumed by FA Public.

## 5. Privacy / erasure inventory (D-159)

Authorized anonymization = `SELECT fa4_anonymize_project(project_id, actor, reason)` (owner-only, SECURITY DEFINER, logged). No automatic retention/purge is invented; **retention periods are an EXTERNAL legal decision**.

| Table | Personal / client data | On erasure |
|---|---|---|
| `fa4_project` | email, answers | email pseudonymized, answers `{}`, status ANONYMIZED |
| `fa4_result` | `model`, `source_snapshot`, `resolution_snapshot` (client texts) | all three replaced by `{"anonymized": true}`; envelope versions kept |
| `fa4_demand_signal` | `payload` | replaced; structured business fields (destination/capability/class) kept |
| `fa4_contact_request` | name, company, email, message | replaced |
| `fa4_access_token` | token hashes | revoked (sessions/links dead) |
| `fa4_legal_acceptance` | document version/url/time (legal evidence, no PII) | **kept** |
| `fa4_marketing_consent` | consent decision/time (no PII) | kept |
| `fa4_email_delivery` | no address, no body (only ids/status/error) | nothing to scrub |
| `fa4_event` | no PII (visit id, step, props: destinations/activities) | kept |
| `fa4_continuation_request` | ids only | kept |
| `fa4_privacy_erasure_log` | actor + reason | the evidence itself |
| catalog tables | none | n/a |

Proven by `fa4-v1-delivery.int.test.ts` («no readable copy … in ANY fa4 table»), which scans every `fa4_*` table for a unique marker and the e-mail address.

## 7. Migration safety and rollback

- 0022/0023 are additive: new nullable/defaulted columns, partial unique index, triggers, replaced anonymization function. Pre-v1.0 `fa4_result` rows (previews that were recorded as results) are **kept and flagged `legacy_unsealed = true`**; they are *not* backfilled with an invented envelope, are never DELIVERED, never eligible for Precision or continuation, and do not block editing. Their projects are normalized to IN_PROGRESS.
- Internal staging (disposable test data): forward migration is safe; resetting the staging DB is also acceptable. **Production has no pre-v1.0 data** (never deployed), so the production migration starts clean.
- Rollback: application rollback (previous Cloud Run revision) is safe only **before** the first real delivery. After deliveries exist, the older code would not understand `legacy_unsealed`/sealed rows (it would treat them as previews). The migrations are not reversed by a revision rollback; a DB rollback would require a restore from backup. No claim of «zero-risk rollback» is made.
